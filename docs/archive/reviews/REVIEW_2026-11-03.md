## 一、总体结论

**这是一个工程质量显著高于行业平均线、但存在若干「门禁盲区」型缺陷的项目。**

先说实力面，这些都是我实测而非采信自述的：

| 维度 | 实测结果 |
|---|---|
| 静态检查 | `ruff` 全部通过（含 C901 复杂度≤6、S 安全规则） |
| 类型检查 | `mypy --strict` 203 个文件 0 错误，仅 3 处 `type: ignore` |
| 测试 | 440 个测试全绿，53 秒 |
| 覆盖率 | **92%**（10081 语句 / 761 未覆盖） |
| 文件级循环依赖 | **0 个**（Tarjan SCC 全图扫描） |
| 领域模型不可变性 | 21 个值对象全部 `frozen=True, extra="forbid"`，无 mutable 容器字段 |
| 端口隔离 | 29 个 Protocol 全部 ≤5 方法，实测无超标 |
| 门面契约 | `ICognitiveCoreFacade` 5 方法，实现精确匹配，无旁路泄漏 |

几个**超出预期**的亮点：

1. **`domain/` 层真正的零依赖**。它连 `sqlite3` 都不 import，`SqliteDatabase.connect()` 返回抽象的 `IAsyncSqlStore`。这是我见过少数没有「领域层偷偷连数据库」的项目。
2. **鉴权设计是 fail-closed 的**。`web/auth.py` 里未配置 token 时**关闭**非 loopback 访问，而不是放开。我专门验证了 DNS rebinding 场景（Host 头伪造为公网域名 → 拒绝）和 Origin 校验，都正确拦截了。这在个人项目里几乎见不到。
3. **监听 `0.0.0.0` 但没有 `trust_env`**、`httpx.AsyncClient(trust_env=False)` 防代理污染、审计表只记 path 不记 query（避免 token 落盘）——这些细节说明作者认真想过威胁模型。
4. **测试用真 SQLite 而非 mock**：全库 440 个测试只有 3 处 mock，1385 个断言，平均每测试 3.1 个断言。我不需要怀疑「测试是摆设」。
5. **`docs/capabilities.json` 的自我评估极其诚实**——主动标记了 12 项 `partial` 和 3 项 `contradicted`（含「7 道门禁只兑现 5 步」「operator 有情感特权」「mind/ 仍有 40+ 处硬编码词表」）。这份台账的可信度比大多数商业项目的能力矩阵都高。

所以下面的问题，需要放在「基线已经很高」的前提下来读。

## 二、缺陷清单

### P1 — 工具选择表存在幽灵工具名，且静默降级（已复现）

`src/echomind/mind/cybernetics.py:42-43` 引用了两个**从未注册**的工具：

```python
REAGENT_TOOLS = {
    ...
    "社交防忽悠核查剂": (
        "recall_memory", "get_group_members",
        "memory_append", "qzone_publish", "profile_signature",
    ),
}
```

实测全量工具名（源码提取）共 **20 个**，试剂表引用了 **21 个**：

- **幽灵引用**：`qzone_publish`、`profile_signature` — 全仓库除这两行外无任何出现，无工具类实现
- **永不被选中**：`qzone_showcase`（实际注册名）— 任何试剂都不会选中它

实际后果被 `src/echomind/extensions/registry.py:126-129` 放大：

```python
chosen = [t for t in enabled_tools if t.name in allow] if allow else enabled_tools
target = chosen if chosen else enabled_tools   # ← 关键
```

`chosen` 为空时**回退成全量 20 个工具**。也就是说：如果某个试剂的名字全部拼错，它不但没把工具收窄，反而塞给 LLM 比预期小数倍的全量 schema（约 3.5k tokens / 轮）。这是一个**静默**降级——无日志、无告警、无测试。

**根本原因**：工具名是裸字符串，`REAGENT_TOOLS`（mind 层）与工具注册表（tools 层）之间没有编译期约束，也没有一致性测试。而 mind 层按架构契约不能 import tools 层，所以这个约束**只能由测试守护**——但它没有被守护。

`tests/unit/test_cross_session_tool_visibility.py:10` 只断言了 `"send_to_chat" in REAGENT_TOOLS[...]`，方向反了。

**建议**：
```python
# tests/architecture/test_reagent_tool_names.py
def test_every_reagent_tool_name_is_registered():
    from echomind.mind.cybernetics import REAGENT_TOOLS
    registered = {cls.name.fget(cls.__new__(cls)) for cls in all_tool_classes()}
    phantom = {t for names in REAGENT_TOOLS.values() for t in names} - registered
    assert not phantom, f"试剂引用了未注册的工具: {phantom}"
```
同时把 `registry.export_openai_tools` 的空集回退改为显式日志或抛错，避免静默放大。

### P1 — trace 写库失败会丢弃已经计费的 LLM 调用，并触发全链重放（已复现）

`src/echomind/adapters/llm/client.py:175-191`：

```python
try:
    resp = await self._call_endpoint(...)      # HTTP 成功，已经计费
    await self._record_trace(gw, ..., chat_key=chat_key)   # 写 SQLite
    return resp                                 # ← 只有前面都成功才 return
except Exception as exc:
    last_exc = exc                              # ← trace 写库异常也落进这里
```

`_record_trace` 内部是裸的 `conn.execute` + `conn.commit()`，没有任何 `try/except`。**可观测性写入和业务返回被放进了同一个 try 块**，于是：一次成功的、已经计费的模型调用，会因为「审计表锁冲突」被当成端点故障丢掉，然后去下一个端点**重新计费重放**。N 个端点全部写库失败 = 一次用户请求产生 N 次计费调用。

我实测复现：
```
★ 故障传导: LLM 调用本身成功, 但因 trace 写库失败而抛出: RuntimeError: database is locked
```

**建议**：把 trace 写入移出故障判定路径，并自行吞掉异常（trace 是旁路观测，不该有权限否决主流程）：

```python
resp = await self._call_endpoint(...)   # 只有这里失败才进入 failover
try:
    await self._record_trace(...)
except Exception:
    logger.warning("trace write failed, ignored", exc_info=True)
return resp
```
同样的模式也出现在 `src/echomind/web/app.py:246-258` 的审计中间件：`write_audit` 没有异常保护，写库失败会让**业务请求本身** 500。

顺带：`_call_endpoint` 里 `max_tokens` 无上限校验（`client.py:153`），调用方传什么就发什么。`agent_runner.py:178` 固定 1200，尚可，但端口层缺一个兜底 clamp。

### P2 — 架构门禁存在结构性盲区：`core/` 完全未被扫描（已复现）

`tests/architecture/test_solid_boundaries.py:22-31` 的黑名单：

```python
FORBIDDEN_IN_DOMAIN_AND_MIND = {
    "aiosqlite", "httpx", "websockets", "fastapi", "nonebot",
    "echomind.adapters", "echomind.web", "echomind.tools",
}   # ← 没有 "echomind.core"
```

而该测试只扫描 `domain/`、`mind/`、`tools/`、`extensions/`、`runtime/` 五处，**`core/` 包从未被任何架构测试扫描**。

我做了注入实验（已还原）：在 `mind/naming.py` 里加入 `from echomind.core.config import AppConfig`，架构门禁 **6 项全部通过**。

这在当前是**潜在**而非**现实**的漏洞（`core/config.py` 只依赖 pydantic，目前 mind/ 也确实没有 import core/）——但 `core/` 里有 `bootstrap.py`（组合根，import 了全部 adapters）。一旦有人图方便从 mind/ 引一个 core 里的配置对象，`mind/` 就通过 `core/` 间接耦合到了全部基础设施**而不触发任何告警**。这正是"六边形被绕穿"最常见的形态。

**建议**：
```python
FORBIDDEN_IN_DOMAIN_AND_MIND |= {"echomind.core"}   # mind/tools/extensions/runtime 一律不许依赖 core
# 并把 "core" 加入需要扫描的包列表（不过 core 是组合根，扫描规则应允许它 import adapters）
```
注意方向：`core/ → adapters/` 合法（组合根本职），`mind/ → core/` 必须禁止。这两个方向同一个包，规则要分开写。

### P2 — 海马体提示词在导入期冻结，人格改名后仍自称旧名（已复现）

`src/echomind/mind/hippocampus.py:19-38`：

```python
HIPPOCAMPUS_INSTRUCTIONS = (
    f"你是「{bot_naming().display()}」大脑中的海马体记忆巩固与自我反思中枢。",
    ...
    f"『某人开玩笑忽悠{bot_naming().label()}说…』",
)
```

这是**模块级常量**，`bot_naming()` 在 `import echomind.mind.hippocampus` 的瞬间就被求值并固化成字符串。而 `set_bot_naming()` 要等到 `core/bootstrap.py:127` 才调用。实测：

```
导入期常量已冻结为: '你是「回音（尾尾）」大脑中的海马体记忆巩固与自我反思…'
set_bot_naming(小鲸鱼) 之后, 常量内容: '你是「回音（尾尾）」大脑中的海马体记忆巩固与自我反思…'
结论: ★ 常量不随改名更新
```

也就是说：控制台改人格名后，**所有其他提示词都更新了，唯独记忆巩固提示词继续用旧名**。人格一致性是这个项目的核心卖点（`CAP-PERSONA-SINGLE-SOURCE` 标为 implemented），这里是个真实的一致性破口。而且它是静默的——不会有任何报错，只会在长期记忆里沉淀出「回音（尾尾）」的错误自我叙述。

`mind/` 内共有 11 处 `bot_naming()` 调用，只有 `hippocampus.py` 这两处是模块级求值。

**建议**：改为函数，在调用时求值：
```python
def _hippocampus_instructions() -> tuple[str, ...]:
    label = bot_naming().label()
    return (
        f"你是「{bot_naming().display()}」大脑中的海马体记忆巩固与自我反思中枢。",
        ...
    )
```
并加一条回归测试：`set_bot_naming(新名); assert 新名 in build_hippocampus_messages(...)`。
这也顺带会让 `test_persona_single_source.py` 更名副其实——目前它是靠检查「默认值是否只有一处定义」实现单源，没覆盖「运行时改名是否一致传播」。

### P2 — WebSocket 事件处理无并发上界（已复现）

`src/echomind/adapters/onebot/live_client.py:264`：

```python
async def _consume_ws_stream(self, ws, stop_event):
    async for raw in ws:
        ev = json.loads(str(raw))
        if isinstance(ev, dict):
            asyncio.create_task(self.handle_raw_event(ev))   # ← 不保存引用、不设上限
```

我没有复现出"任务被 GC 掉"——在 CPython 下 `asyncio` 的 `_all_tasks` 弱集合实际会保活（实测 2000 个任务全部存活）。**但这比 GC 更糟**：实测 2000 条消息 → 2000 个并发任务，无任何背压。

后果是每个事件都要走一遍 `expand_incoming_forward → pipeline.process → transcribe_incoming_voice → save_incoming → evaluate_incoming`，其中含 HTTP 调用和 LLM 调用。一个 500 人的群刷屏时，会产生数百个并发协程同时抢 SQLite 写锁和 LLM 配额。

**缓解措施确实存在但不覆盖这段**：`handle_raw_event` 里有 `_wake_scheduled` 去抖（`:247-255`）和 `_drain_chat_batches` 的 per-chat `asyncio.Lock`（`:219-220`），**这保证了同一会话内不并发**——这是我最担心的问题，作者已经解决了。但去抖发生在 `evaluate_incoming` **之后**（`:242`），也就是说前面那串 I/O 仍然是全量并发，且跨会话无上界。

**建议**：用一个带信号量的有界队列替代裸 `create_task`：
```python
self._sem = asyncio.Semaphore(32)          # 或按 chat_key 分片
async def _guarded(self, ev):
    async with self._sem:
        await self.handle_raw_event(ev)
```
并把 `_wake_scheduled` 的去抖提前到 `parse_onebot_event` 之后、任何 I/O 之前。另外应持有 task 引用集合 + `add_done_callback` 移除，这是 asyncio 的标准实践，也让优雅停机可以 `gather` 等待在途任务。

### P3 — 类型契约的"软逃逸"：`getattr` 兜底与 `Any` 参数

项目对外宣称 DIP-01「构造函数依赖必须全部声明为 Protocol」，这条**确实被遵守了**。但函数内部存在 22 处 `getattr(obj, "...", None)` 式的结构化兜底，绕过类型系统探测能力：

```python
# src/echomind/tools/member_memory.py:123
loader = getattr(self._reader, "get_cross_session_facts", None)
return (*facts, *await loader(chat_key)) if callable(loader) else facts

# src/echomind/mind/relation_persist.py:13   —— 连参数类型都退化成了 Any
async def persist_relations(writer: Any, relations: tuple[MemoryRelation, ...]) -> int:
    upsert = getattr(writer, "upsert_relation", None)
    if upsert is None:
        return 0
```

`relation_persist.py` 的 docstring 写得很明白——"without widening IMemoryWriter"，这是在**遵守 ISP-02（端口≤5方法）的前提下，用 `Any` 加 duck-typing 绕开了类型系统**。动机可以理解，但结果是：mypy 在这里完全失效，`persist_relations` 传入任何对象都能通过检查，而错误要等到运行时静默 `return 0`（记忆关系丢失且不报错）。

同类还有 `frame_renderer.py:49-51`（`getattr(affect, "jealousy", 0.0)`，而 `AffectiveVector` 是已知的冻结值对象，直接 `.jealousy` 即可）、`disclosure.py:50-51`。

**建议**：为这类能力定义窄端口，而不是 `getattr` 探测。记忆读写本来就有 `IMemoryReader`，跨会话读取可以再加一个 `ICrossSessionFactReader(Protocol)`（1 个方法），让实现类显式挂载；这既满足 ISP 又恢复类型安全。`frame_renderer` 那三处直接改成属性访问即可，没有任何理由用 `getattr`。

### P3 — 单实现的 "运输层" Protocol 偏仪式化

`adapters/llm/client.py:20` 的 `IHttpPostTransport`、`tools/cnmeme_wiki.py` 的 `IHttpGetJsonTransport`，各自只有一个生产实现 + 测试替身。它们是**为可测试性而生的接缝**（这点合理，比 mock `httpx` 干净），但被放在 `adapters/` 内部定义而非 `domain/`，说明作者也下意识觉得它们不是真正的领域端口。

另外 `HttpxPostTransport.post_json` 每次都新建 `httpx.AsyncClient`（`:31`），没有连接池复用。在「每轮 LLM 调用 + 每个 tool 调用」的频率下，这会造成 TCP/TLS 握手开销和 TIME_WAIT 堆积。建议在网关实例上持有一个长生命周期 client，并在 shutdown 时 `aclose()`。

死代码方面：codegraph 标出约 210 个符号无入边，抽样确认绝大多数是 `domain/` 的 Protocol 定义（正常，接口无调用边）和 `__init__` 导出，**没有发现实质性死代码**。这是好的信号。

## 三、值得肯定但容易被误判的设计

写在这里，因为在评审中它们看起来像问题、实际是正确决策：

1. **17 个 Repository 各自 `new SqliteRelationStore(self._db)`**（`memory_repo.py:222` 等处）看似 Dubbo 式硬耦合，实际是组合根模式——`mind/` 侧只见到 `IMemoryReader`。`codegraph impact SqliteDatabase` 报 855 个受影响符号，这是**组合根的正常代价**，不是 God object 的味道。不过需要注意：这意味着 `SqliteDatabase` 一旦改接口，测试和脚本会大面积连带失败。

2. **SQL 里 11 处 f-string 表名**（`# noqa: S608`）经核查全部来自固定字典（`_TABLES = {"semantic": "semantic_facts", ...}`）或字面量，用户数据一律 `?` 参数绑定。**不存在注入面**，`noqa` 是正当的。

3. **`test_solid_boundaries.py` 的 `_calc_max_nesting(fn, 0)` 从函数体起算深度**，`flattened` 严格到 2 层，比宣称的还严——这条门禁是真的在起作用（203 个文件、所有函数都 ≤40 行、嵌套 ≤2）。

4. **`CAP-OPERATOR-NO-PRIVILEGE` 标为 contradicted**：`update_sender_bond` 对 owner 直接置 `trust=1.0`。作者自己发现了。从产品角度这未必是 bug（群主特权是设计选择），但和声明的「operator 无情感特权」矛盾——**建议改声明而不是改代码**。

## 四、优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P1** | 修 `REAGENT_TOOLS` 幽灵工具名 + 加一致性测试 | 已在影响线上工具选择，且静默放大 token 成本 |
| **P1** | trace/audit 写入移出故障路径 | 会导致重复计费 + 业务误失败，线上直接烧钱 |
| **P2** | 架构门禁加 `echomind.core` 并扫描 core 包 | 目前无害，但这是最容易在未来被绕穿的缝 |
| **P2** | 海马体提示词改为运行时求值 | 人格改名不一致，会污染长期记忆叙事 |
| **P2** | WS 事件加并发信号量 + 任务引用集合 | 抗刷屏能力，也是优雅停机的前提 |
| **P3** | `getattr`/`Any` 兜底收敛为窄端口 | 恢复 mypy 在记忆关系持久化路径上的保护 |
| **P3** | httpx client 复用 | 降低延迟与 fd 压力 |
| **P3** | 补充并发/竞态测试（目前仅 `test_working_versions.py` 一处） | 442 个测试里几乎不覆盖并发语义，而这是 webhook 型服务的核心风险 |

## 五、给作者的一句话

这套「架构契约 + AST 门禁 + 参数台账 + 能力台账」的工程体系，在个人项目里是罕见的严肃态度——**mypy strict 零错误 + 92% 覆盖率 + 零循环依赖 + 21 个冻结值对象**，这些指标放在商业团队里也拿得出手。

但本项目最大的系统性风险，恰恰是**门禁的可信度本身**：上面 4 个缺陷（幽灵工具名、trace 阻塞主流程、core 未扫描、导入期冻结）**全部穿过了现有全部门禁**，且都不触发任何告警。当一套门禁足够强时，人会本能地信任它，从而停止人工审视——这是"质量体系的成功带来的失败"。

建议在 `capabilities.json` 里补两条：
- `CAP-REAGENT-TOOL-REFS`：试剂引用的工具名必须存在于注册表
- `CAP-OBSERVABILITY-NONBLOCKING`：审计/追踪写入失败不得影响主流程

这两条的验收测试都很小，但它们守护的是**「体系自身不出错」**这一层，比再补 10 个覆盖率测试更有价值。
