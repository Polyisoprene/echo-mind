### ✅ 1. 幽灵工具名 —— 成立，且已精确定位

上一轮我是从源码正则提取工具名（20 个）。本轮改用**真实装配路径**（`main.py:_register_skill_tools` 的完整注册列表 + 反射 `name` property），得到完全一致的结果，但**影响面比原报告描述的更精确**：

真实已注册工具数: 20

**关键收窄**：幽灵名只污染「社交防忽悠核查剂」一个试剂，其余 4 个试剂干净。原报告给人的印象是所有试剂都受影响，实际不是。

所以准确表述是：**LLM 主动发说说的能力是断的，只有定时调度器那条路通**。这是能力缺口，不是崩溃。严重度维持 P1，但性质从"工具丢失"改为"入口缺失"。

### ✅ 2. trace 阻塞 —— 成立，且比原报告更严重

上一轮我用了一个假的 `BrokenTraceDb` 对象。本轮改用**真实 `SqliteDatabase` + 真实 `FailoverLlmGateway` + 真实链路**，通过删除 `llm_traces` 表制造真实的 `sqlite3.OperationalError`：

```
[正常] 返回成功, HTTP 调用次数=1
[故障] ★ 业务失败: OperationalError: no such table: llm_traces
[故障] HTTP 实际调用次数 = 2  (链上端点 = 2)
  ★★ 已计费的模型调用被重放 2 次 —— 每次都是真实计费
```

**这比原报告说的更严重**：原报告说"会去下一个端点重放"，实测证明**每个端点都会被重放一次**，即 N 个端点 = N 次计费。而且 `_record_trace` 内部经确认**无任何 try/except**（`client.py:101-133`）。

同类问题在审计中间件也复现了（`app.py:246-258` 的 `write_audit` 无保护，写库失败会让业务请求直接 500）：

```
[审计] ★ write_audit 抛出: OperationalError: table admin_audit has no column named ts
```

这个模式的共性是：**把旁路可观测性写入和业务返回放进了同一条故障判定路径**。

### ✅ 3. 门禁盲区 —— 成立，且这次找到了文档依据

上一轮我只说"黑名单漏了 `core`"。本轮我去查了文档，得到了**决定性证据**：

> `docs/architecture/ARCHITECTURE_CONTRACTS.md:15`
> `| **mind/** | Layer 1 · 认知核心层 | ... | 仅 domain/ | 严禁导入 adapters/、web/、tools/、aiosqlite、httpx、nonebot、fastapi |`

文档明确规定 `mind/` **"仅 `domain/`"**。因此导入 `core/` 属于**违反文档契约**，而不只是"黑名单没写全"。黑名单是实现，文档是契约——**实现没兑现契约**。

严格实验（带 sha256 校验的注入，已精确还原）：

```
原始 sha256: 065c661d889fc6f930ca93279a5d98b02d1f33d0be5dd1e8f08aadb3122f2976
[注入 mind/naming.py: from echomind.core.config import AppConfig]
12 passed  ← 全部门禁通过
[还原后 sha256 一致]
```

并且我进一步验证了**实际危害不是理论**：

```
★ 可从 mind 侧触发 core.bootstrap 导入: EchoMindContainer
★ 此时 adapters 已加载: True
★ 已加载的 adapters 子模块数: 31
```

即：`mind/ → core → bootstrap → 31 个 adapters 子模块`。**一条 import 就能让认知核心层反向依赖全部基础设施，而门禁零告警。** 这是六边形架构被绕穿的最典型形态。

建议的修法要区分方向：`core/ → adapters/` 合法（组合根本职），`mind/ → core/` 必须禁止。同一个包两个方向，规则要分开写。

## 三、需要修正的两处原报告表述

### ⚠️ 修正 1：空集回退"静默放大 token" —— 本版本不可达

原报告（第 67、82、277 行）把"`chosen` 为空 → 回退全量 20 个工具"说成一个正在发生的问题。本轮逐试剂枚举后：

```
日常轻装剂: 下发 6 个
多模态鉴赏剂: 下发 5 个
百科求真剂: 下发 5 个
声情共鸣与点歌剂: 下发 4 个
社交防忽悠核查剂: 下发 3 个     ← 有命中, 不是空集
```

**没有任何试剂触发空集回退**。该路径在本版本是**不可达的**。

准确表述应为：这是一个**潜在**的静默降级路径——只有当某个试剂的名字被集体改错时才触发，届时会静默下发全量 20 个工具而无任何告警。它是一项**防御性加固建议**，不是当前正在发生的成本浪费。

原报告在此处把潜在风险表述成了现实问题，这一点我上一轮判断有误。

### ❌ 修正 2：任务 GC —— 措辞有误

原报告第 198 行已自己澄清了"没有复现出任务被 GC"，但标题和上下文仍留有"未持有引用 → 可能失联"的暗示。本轮实测：

```
500 个未保存引用的 task, gc 后仍存活 = 500 / 500
→ CPython+asyncio 的 _all_tasks 弱集合会保活, 不会被 GC
```

**应明确删除"GC 风险"这一说法。** 真正的问题是并发无上界（第 5 条），以及缺少任务引用集合导致**无法优雅停机**（拆机时无法 `gather` 等待在途任务）。这是两件不同的事，不应混为一谈。

## 四、新增发现

### 🆕 A. GIF 解码在事件循环中同步执行（P2）

`media_gateway.py:118` 直接调用 `gif_to_storyboard_data_url`，而 Pillow 解码是纯同步 CPU 操作。**同一个文件**的 video 路径却正确使用了 `asyncio.to_thread`（`:155,158`）：

```python
raw_urls = await asyncio.to_thread(self._extract_frames, str(video_file), count)  # ✓
...
return gif_to_storyboard_data_url(raw) or _to_data_url(raw, "image/gif")          # ✗ 同步
```

实测：

```
GIF 大小: 50 KB, 帧数 60
gif_to_storyboard_data_url 同步耗时: 105 ms  (期间事件循环完全阻塞)
若同时有 10 个并发会话各发一张 → 累计阻塞约 1051 ms
```

群聊刷表情包时，所有会话的心跳、SSE、消息收发都会被这 105ms/张 卡住。**作者明显知道 `to_thread` 这个模式却漏了这一处**，是典型的局部不一致。修法就是把该行包进 `await asyncio.to_thread(...)`。

### 🆕 B. Token 非常量时间比较（P3）

`web/auth.py:59`：

```python
token_ok = _extract_request_token(request) == auth_key
```

应改用 `hmac.compare_digest`。实际风险很低（网络抖动远大于时序差异，且 token 是本地生成的高熵值），但这是安全清单里的标准项，一行即可修。

### 🆕 C. 文档与实现存在系统性漂移（P2，与"门禁可信度"主题一致）

用 AST 比对文档声明与实际：

| 文档声明 | 实际 | 位置 |
|---|---|---|
| `ICognitiveCoreFacade` **4 个**顶层方法 | **5 个** | `ARCHITECTURE_CONTRACTS.md:51` |
| `mind/` 仅依赖 `domain/` | 门禁未强制（见复核 3） | `ARCHITECTURE_CONTRACTS.md:15` |
| 7 道自动化门禁 | 脚本 8 个 Gate 标签、含 1A/1B/1C/2/2B/2C/3&4/2D | 与 `capabilities.json` 自述"实际 5 步"三方不一致 |

第三条尤其值得注意：**文档说 7 道、脚本有 8 个标签、capabilities.json 说"实际 5 步"**——三份材料对同一件事给出三个数字。这类漂移本身不致命，但它侵蚀的恰恰是"契约可信"这个本项目最核心的资产。

另外我实测了门禁的可执行性（这是上一轮没做的）：`radon` 平均复杂度 B (7.40)、超阈值 0 个；`pylint` 10.00/10；`eval/baselines/2026-10.json` 存在；`uv` 可用。**门禁不是装饰，确实能跑通。** 这一点应补充为对项目的正面评价。

## 五、全局建模结论

把 11 条放在一张图上看，它们不是 11 个孤立 bug，而是**同一个结构性弱点的 11 次显影**：

> **本项目把"约束"从人的注意力里搬进了机器门禁，但门禁的覆盖面本身没有被覆盖。**

具体表现为三种空白：

1. **跨包的"名实一致性"无人守护** — 工具名字符串（4、1 条幽灵）在 mind 层与 tools 层之间没有编译期约束，因架构契约禁止 mind import tools，这个约束**只能靠测试**，而测试方向写反了。
2. **旁路代码（trace/audit）与主流程共享故障判定** — 2、A、B 三条。
3. **文档契约与静态门禁的差集** — 3、C 三条。

而这三类空白有一个共同性质：**它们都不会在测试里失败，只会在生产里显形**。这正好解释了为什么一个 ruff+mypy+92%覆盖率的项目仍能带着这些缺陷跑。
